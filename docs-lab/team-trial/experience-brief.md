# Experience brief: from solo use to team practice

**Target experience.** A team deciding “we'll try OpenSpec together” can bring it to an existing repo without adopting a new service, schema, or review system. In one short kickoff, they choose a real change and a useful question to answer. A proposer makes intended behavior and implementation choices reviewable *before* costly execution; a different engineer can challenge, continue, and ship from repo-versioned artifacts, without the first person's chat history. When work finishes, the resulting current specs and archived change become durable team context. Over repeated changes, the team evolves a few shared conventions and can judge when OpenSpec adds value, when it doesn't, and where it needs adjustment.

**Shared versus personal.** Share project context, change intent, selected tool integrations, the decisions behind requirements, normal PR checkpoints and the final record. Keep agents, credentials, model choice, local CLI installation, chat sessions and global preferences personal. A team has adopted OpenSpec when **someone other than the author reviews or advances the same versioned change** and the repo/PR becomes the point of coordination; merely having multiple CLI installs is not adoption.

**First slice: a one-change, one-week trial kit.** Deliver a self-contained Markdown handout that uses `openspec init`, a small `openspec/config.yaml`, the default propose → apply → archive path, a human review before code, an explicit fresh-session handoff, one midweek check, and a continue/adjust/stop decision. This is stronger than a setup tutorial: its core unit is a *team decision transferred between people*. It is also cheaper and more adaptable than a hosted trial wizard. Teams customize only real project facts and one improvement signal. A schema is not a starting decision.

**Deliberately outside scope.** No workspace/server, centralized policy, universal adoption score, automatic enforcement, CI gates, bespoke schema, enterprise rollout, multi-repo stores, or quantified productivity claims. No blanket mandate to spec every change. A one-week window is enough to test comprehension and friction, not causality or ROI.

**Design hypothesis (not yet proven).** A small pre-code plan review plus a fresh-chat handoff will make the value legible more quickly than a comprehensive training session. The test is a real pair using their own repo and agents, not a single-person demo.
